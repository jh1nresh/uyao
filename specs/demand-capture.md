# 需求捕捉：落空搜尋 + 到貨通知

> 2026-08-05 · 消費端 `web/` · 前置：無（不需要任何盒子上線）

## 為什麼現在做

站上目前 **166 家真藥局、14 支藥、0 筆庫存**。每一次搜尋的結局都是兩種落空之一，
而**兩種都被丟掉了** —— 沒有記錄、沒有通知登記、沒有任何 API 接住。

落空的搜尋是這個產品最值錢的訊號：**一筆帶地點與時間、已經證明存在的需求**。
它比任何預測都準，而且**不需要等盒子上線就開始累積**。等第一台盒子裝好時，
我們已經知道中山區的人在找什麼。

它同時是三件事的輸入：

| 用途 | 怎麼用 |
|---|---|
| 藥局招募 | 「你這區這個月有 37 個人在找你沒進的貨」—— 比任何話術有力 |
| 目錄擴充 | 目錄只有 14 支。搜不到的字就是該加的品項 |
| 之後的過剩媒合 | 藥局有賣不完的批次時，先問「附近有沒有人搜過這支」 |

## 兩種落空要分開記

| 類型 | 發生在 | 意義 | 現在的畫面 |
|---|---|---|---|
| `catalog_miss` | `/search` | 查詢對不到目錄裡任何一支藥 | 「附近沒有符合的品項」 |
| `inventory_miss` | `/drug/[slug]` | 藥在目錄裡，但沒有藥局有庫存 | `NoInventoryYet` |

目前 `OFFERS` 是空的，所以**每一次藥品頁瀏覽都是 `inventory_miss`**。
這不是 bug，是現在真實的狀態。

## P1（這次做）

### 1. 被動記錄

兩個空狀態掛載時各送一筆 `POST /api/demand`，不需要使用者做任何事。

- **只記查詢內容、藥品 slug、地區、時間戳**。不記 IP、不做指紋、不放 cookie
- 走 client 端掛載而不是 server render：避免 prefetch 與爬蟲灌水，也不在
  render 裡做 side effect。代價是**沒有 JS 的訪客不會被記到** —— 這個訊號
  本來就只需要方向性，可接受

### 2. 到貨通知登記

兩個空狀態各放一個表單：聯絡方式 + 地區。送出後同一個 endpoint，多帶 `contact`。

**文案不能承諾我們做不到的事。** 現在沒有庫存流，所以不能寫「有貨就通知你」，
要寫成「這一區有藥局裝上盒子、而且這支有貨時通知你」—— 這是真的。

### 3. 儲存

`web/.data/demand.jsonl`，跟 `reservations` / `pilot` 同一個 pattern（gitignored）。

```jsonc
{
  "at": "2026-08-05T...",
  "kind": "catalog_miss" | "inventory_miss",
  "query": "腰痛貼的那個",   // 原始輸入，未正規化
  "drugSlug": "salonpas-ae", // inventory_miss 才有
  "area": "zhongshan",
  "contact": "..."           // 只有主動登記才有
}
```

**`query` 一定要存原話。** 正規化（同義詞、錯字、症狀→成分）是之後的事，
可能會用 LLM 做；把原始輸入丟掉就永遠補不回來。

## LLM 放在哪（不是這次做，但架構要留位）

這條鏈上絕大多數是算術與規則，不需要模型：

| 步驟 | LLM？ |
|---|---|
| 記錄、彙總、比對地區 | ❌ |
| 「這區這個月多少人找這支」 | ❌ group by |
| **把「腰痛貼的那個」對到 SKU／成分** | ✅ 唯一真正模糊的地方 |
| 數量、效期、價格判斷 | ❌ **絕對不行**，要負責任的數字不能生成 |

因此 P1 的唯一架構要求就是**存原始 query**，讓之後的正規化可以離線重跑歷史資料。

## 驗收

1. `/search?q=<不存在的字>` → 空狀態出現通知表單，`.data/demand.jsonl` 多一筆 `catalog_miss`
2. `/drug/<slug>` → `NoInventoryYet` 出現通知表單，多一筆 `inventory_miss`
3. 送出聯絡方式 → 同一筆類型再多一筆，帶 `contact`，畫面有 inline 成功訊息
4. 空的聯絡方式擋在前端；壞 JSON / 缺欄位回 4xx
5. `next build` + `tsc --noEmit` 乾淨；字型 subset 重跑後全站 0 字漏

## 不做

- 真的寄出通知（沒有庫存流可觸發，也還沒有寄送管道）
- 查詢正規化 / 同義詞（留給之後，靠存下來的原話離線重跑）
- 後台介面（先用 `jsonl` + `jq`，有量再說）
- 動搜尋排序 —— 排序是誠實分級的一部分，需求資料**只能用來回填使用者主動要求過的通知**，
  不能拿來把某家店排前面

## 已知限制

- 藥品頁是 SSG，`area` 目前寫死 `DEFAULT_AREA`。表單讓使用者自己選區（預設帶
  網址上的 `?area=`），所以地區資料靠使用者確認而不是推斷
- 地區選擇不會在導覽間保留（`AreaSwitch` 只連回首頁），這是既有問題，不在本次範圍
